Oscitron → VCV Rack

Assessing a port of the Oscitron eurorack firmware to a VCV Rack plugin — emulation strategy, timing fidelity, output-stage modelling, and integration path.

Summary

Recommendation

Port the DSP natively — don't emulate the AVRRecommended

While building the bare-metal AVR-GCC port earlier in this session, one thing became clear: this codebase already separates cleanly into two halves.

~20 of the 22 libraries are pure DSP/data, with zero hardware register access: AteOscEngine, AteOscOscillator, AteOscPatch, AteOscPitch, AtmPitch, BiquadFilterFM, CvInput, Flanger, Portamento, Pwm, QuantizePitch, Wavecrusher, Wavetable, FixedMath, SsHelpers, RotaryEncoder, Switch, LedCircular, LedRgb. These compile as ordinary C++ on any platform once avr/pgmspace.h's PROGMEM/pgm_read_* macros are shimmed to no-ops — FixedMath.h is a good example, pure lookup tables, no inline assembly.

Only 2 libraries touch AVR hardware directly: AteOscHardware.cpp (ADC, TWI/I²C, GPIO, EEPROM) and AtmAudio.cpp (Timer1/Timer2 audio output). Everything hardware-specific is already concentrated where you'd want it for a port.

Instruction-level AVR emulation is real, proven technology — but it solves a much harder problem than this port needs, moving the risk from "does the DSP sound right" (answerable by ear, against your own hardware, quickly) to "did I model the ADC/TWI/timer peripherals correctly" (answerable only by deep AVR peripheral archaeology). Spend the effort on reproducing the specific, characterful non-idealities faithfully — not on reproducing the chip that produces them.

Both paths are viable engineering projects. Both are covered in full below, since you asked for both, along with where they intersect.

Part 1 of 5

01 Functional-level emulation — native port

What it is: compile the existing DSP libraries (unmodified engine logic) as native x86/ARM C++, and replace AteOscHardware/AtmAudio with a thin adapter mapping VCV Rack's params/inputs/lights onto the interface the engine already calls — hardwareCvInputChanged(), hardwareSwitchChanged(), hardwareGateInputChanged() and so on are already the shape of AteOsc.cpp's public surface.

Keep the fixed-point arithmetic

The engine uses int/char/fixed-point throughout — FixedMath.h's 10-bit sine/tan tables, Wavetable's int8_t samples — not floating point. Keep it that way in the port. The specific quantization is part of the sound; "upgrading" to float would silently change the noise floor and rounding behaviour of every filter and oscillator stage.

CV scaling: reuse the firmware's calibration system

CV inputs are 0–5 V; external bipolar LFOs/10V envelopes go through a separate module, UniFive, first. I read UniFive8.sch (the latest of several revisions): it's a trimmer-calibrated op-amp scaling circuit (LM4040 2.5 V references, 3352T trim pots in the feedback path). Its exact transfer function depends on a physical trim pot position not encoded in the schematic — not worth deriving analytically. It doesn't need to be: AteOscHardware.h already has a per-unit calibration system (cvCalib_[2][3], EEPROM_FILT_HIGH/LOW, a whole separate AteOscHardwareCalibrate library) the firmware itself uses to map raw ADC counts to musical values. Port that logic, seeded with either the real module's calibration constants (readable from its EEPROM) or sensible defaults — that's the actual source of truth for CV scaling, not the analog trim network.

Part 2 of 5

02 Accurate-level emulation — instruction/peripheral-accurate

What it is: run the actual compiled firmware — the .elf already built in this repo (Debug/SsAteOscitron.elf) — inside a real AVR CPU simulator, driven cycle-by-cycle from VCV's audio callback, with virtual peripherals standing in for the physical chips.

Recommended core: simavr. Native C, actively maintained, built for exactly this "embed a real AVR core inside a native real-time host" use case — unlike JS-based alternatives like avr8js. Performance is not the blocker: AVR cores at 16 MHz are trivial for simavr to simulate many times faster than real-time on modern hardware, so the constraint is implementation completeness, not CPU budget.

This is proven in VCV Rack specifically, not a novel idea

  • RackNES runs a real NES CPU/APU emulator (derived from SimpleNES + Nes_Snd_Emu) inside a VCV module.
  • KautenjaDSP's plugins emulate the Ricoh 2A03.
  • SID-chip modules (vcvrack-sid, sidex-vcv) do the same for the C64's SID.

A multi-week effort, not a multi-day one — mostly the peripheral-modelling table above, not the CPU core itself (that part is solved, off-the-shelf).

When this is worth it

If bit-exact reproduction of hardware quirks — timer jitter, ADC noise floor, EEPROM-calibration-dependent CV scaling — is a hard product requirement, the way chiptune-emulation plugins market "the real chip, virtualized." If "sounds and behaves the same" is the bar, §01 gets there for a fraction of the effort.

Part 3 of 5

03 Throttling to 16 MHz — audio-identical wavetable timing

This is where the real character of the instrument lives, and it applies to both paths above.

Reading AtmAudio.cpp directly: the audio path is not a fixed sample-rate oscillator. It's built around two timers.

  • Timer2 runs Fast PWM at a fixed ~62.5 kHz carrier (F_CPU/256, unprescaled) — the actual 8-bit DAC. OCR2B is written with sample + 128 each time a new wavetable sample is due.
  • Timer1 runs in CTC mode and fires ISR(TIMER1_COMPA_vect) at a variable rate that is the pitch — setSampleFreq() computes OCR1A directly from the target frequency (ocr = (F_CPU << i) / sampleFreq_). Each firing advances the wavetable read position.
The non-obvious detail

OCR1A is an 8-bit-ish integer divisor of a 16 MHz clock, so it can't represent every frequency exactly. Once the divisor would drop below the safe minimum (~255 counts, per the code's own comment), the ISR starts skipping samples in powers of two (bufferJump = 1 << i) rather than raising the ISR rate further. At higher pitches the wavetable is read with stride > 1 — a reproducible, audible decimation aliasing that's a genuine characteristic of this instrument, not an incidental limitation.

For the native port: don't replace this with a clean floating-point phase accumulator — it will sound smoother than the real hardware, not the same. Port the integer-divisor-plus-stride-doubling arithmetic verbatim, driven by VCV's args.sampleTime accumulating toward the next "virtual ISR" firing.

For the emulated path: automatic and exact, since you're running the literal ISR — the only job left is cycle accounting: step the simavr core round(16'000'000 × args.sampleTime) cycles per process() call, carrying the fractional remainder across calls so it doesn't drift over a session. Standard technique for embedding cycle-accurate emulators in real-time audio hosts.

Part 4 of 5

04 Emulating the OPA2134 output stage

Update — I read the actual schematic

PS_atmega_proto_09.sch (the main board) — Eagle .sch files are plain XML, directly parseable. This revises the recommendation below: the analog stage isn't just inconsequential carrier removal, it meaningfully shapes the audio band — but it's still a linear circuit, not something needing op-amp non-linearity modelling.

Traced signal path, with real values

ATmega PD3 (OC2B, ~62.5 kHz PWM carrier)
  -> R25 (5k1) -> [C7 (10nF) to GND]      passive pole ~3.1 kHz
  -> R29 (2k)  -> [C8 (10nF) to GND]      passive pole ~8.0 kHz (loaded further by R30)
  -> R30 (6k8) -> OPA2134 gate A (-IN), +IN grounded
       feedback: R31 (6k8) || C9 (100pF)   gain -1, HF pole ~234 kHz (stability only)
  -> gate A OUT
       R1 (10k) into gate B (-IN)   [audio path]
       R2 (10k) into gate B (-IN)   [bias path, via R5 (24.9k) from a 2.5V reference]
  -> OPA2134 gate B (-IN), +IN grounded
       feedback: R3 (20k) || C6 (220pF)
  -> gate B OUT = -2 × (gate A audio) - 2 × (2.5V-derived bias, ≈ -1.43 V)
  -> R4 (1k) -> C12 (10µF, AC-coupling) -> output jack
       R4+C12 forms a ~15.9 Hz high-pass: DC block / subsonic filter only

Two things worth calling out:

  1. The two cascaded passive RC poles (~3.1 kHz, ~8 kHz) are doing real work in the audible band, not just killing a 62.5 kHz carrier. The oscillator's sample rate is always high relative to typical pitches — a 128-sample wavetable read out at (pitch × 128), ~56 kHz for a 440 Hz note — so this filter is actively rolling off the top end of the wavetable's own harmonic content. That's part of "the Oscitron sound," not a side effect to ignore. Revised recommendation: model this as a real 2–3-pole low-pass in this range, not a generic placeholder far above the audio band. The stages interact (R30 loads the second pole via the op-amp's virtual ground), so an exact analytical transfer function is fiddly — SPICE-simulating this exact network, or simply measuring the physical module's frequency response directly, will be faster and more reliable than hand-deriving it.
  2. Gate B is an inverting summing amplifier, not a plain buffer: it combines the filtered audio (gain ×2, via R3/R1 = 20k/10k) with a fixed DC bias from a 2.5 V reference, most likely cancelling the built-in offset from the firmware's sample + 128 PWM encoding (§03) before the AC-coupling stage removes whatever DC remains. Net effect for the plugin: linear gain + the filter above — the DC-cancellation arithmetic itself doesn't need reproducing.

What still doesn't matter: the OPA2134's own non-linearity/noise. Nothing in this circuit drives it outside its linear region, and its contribution is negligible next to the 8-bit DAC quantization and wavetable-stride aliasing that are the actual character of the instrument. The correction here is the passive filter's cutoff sitting lower and more consequential than assumed — not the op-amp needing a nonlinear model.

The daughterboard

The rotary encoder LED rings are on a separate board (Euro_LED_PCB_06) with no schematic symbols for the LEDs themselves (raw footprints on the board layout) — but Osci_LED_orientation.png in that folder shows the physical layout directly: two rings of 16 LEDs, one per encoder, around a square encoder cutout. Matches LedCircular.h's own header comment ("Hardware 16 LED array") and its unsigned int bitmask state exactly — confirms the widget spec in §05: 2 instances of a 16-segment circular LED ring.

Part 5 of 5

05 VCV Rack integration

Interfacing with the audio engine

Module::process(const ProcessArgs& args) is called once per audio sample (args.sampleRate / args.sampleTime reflect VCV's engine rate, independently configurable from the audio device's own rate). Standard surface:

  • inputs[X].getVoltage() / outputs[X].setVoltage(v) — eurorack ±5 V / 10 Vpp, matching what Oscitron already outputs as hardware.
  • params[X].getValue() — knob/switch state.
  • lights[X].setBrightness(b) — panel LEDs.

Since the DSP core steps in fixed AVR-clock-relative time (§03), the natural shape is accumulating args.sampleTime toward the next "virtual timer" event inside process() — true whether you go the native-port or emulated-core route.

UI from your source graphics

VCV's workflow: a layered SVG panel with named component nodes, parsed by the SDK's helper.py createmodule <slug> <panel.svg> to auto-generate parameter/port/light declarations and widget placement. Practically: bring your existing panel graphics into an SVG with properly named component layers (Illustrator or Inkscape both work), then let the helper script do the mechanical wiring.

Needs custom widget code, not just the helper script

The panel has 2 rotary encoders, each paired with a LedCircular — a circular ring of LEDs, likely a wavetable-position indicator — and an LedRgb in the switch. VCV's stock widget library has no circular LED-ring component, so this needs a custom LightWidget/ParamWidget subclass drawing N lights in a ring and handling encoder-style interaction (relative drag/scroll, not a knob's absolute angle) — real, bounded work, not a blocker.

The 8 CV inputs — CV_FILT, CV_RES, CV_PITCHPOT, CV_FILTPOT, CV_PITCH, CV_PWM, CV_FLANGE, CV_CAPTURE — map straightforwardly to 8 VCV input jacks.

IDE / toolchain — correcting the VS2026 assumption

Checked rather than assumed, since it directly affects your setup: VCV Rack plugins on Windows are built with MinGW-w64 GCC, not MSVC. The Rack SDK's documented Windows workflow is MSYS2 + mingw-w64-x86_64-gcc, invoked via the SDK's Makefiles — because Rack's own binary and plugin ABI are GCC-built, and mixing MSVC-compiled plugin code with a GCC-compiled host has real, well-known C++ ABI problems (name mangling, exception handling, standard-library internals all differ between the two families). Plain Visual Studio 2026 with its native MSVC backend is not a supported path for the final plugin binary.

Recommendation, in order

→ Suggested path

  1. Native port first (§01). Fastest route to a working, playable VCV module, and where nearly all the actual risk-reduction work — does the port sound and feel like the hardware — has to happen regardless of which emulation strategy you eventually pick.
  2. Get the timing model right (§03) as part of that port. The single highest-leverage detail for "sounds like the real thing," and genuinely cheap to port faithfully rather than approximate.
  3. Treat the OPA2134 stage as a simple filter+gain block (§04), unless the physical module or schematic reveals a surprise — deliberate soft clipping, say — worth preserving.
  4. Revisit full instruction-accurate emulation (§02) only if the native port's fidelity doesn't satisfy you. Real, proven, but substantially larger — and you'd likely be reproducing behaviour the native port already captures if §03 is done carefully.
